# Terraform delivery runbook

Prepared on 29 October 2026. Workflow code is ready for CI verification; Azure execution is disabled until personal targets, cost scope, state and OIDC are confirmed. No cloud resources or Entra identities have been created by this setup.

## Current scope

`foundation/` owns one new resource group named `rg-ai-sre-*`, with fixed project/environment/owner tags and an explicit expiry date. It uses Terraform 1.17.1 and AzureRM 5.11.0. The provider lock is generated by real initialization and includes Linux/Windows checksums. Provider registration is disabled. Deletion is protected in Terraform and when the group contains resources. AKS, networking, registry, Key Vault, Managed and budget alerts remain later costed modules.

CI runs format, backend-disabled initialization, validation, mocked Terraform scope checks and Python delivery-guard tests. CI performs no Azure authentication or cloud plan. The workload repository builds an image but does not publish/deploy it in this stage.

## GitHub environments and trust

The manual `Terraform foundation delivery` workflow accepts only main from this exact organization/repository. Repository variable `AZURE_DEPLOYMENT_ENABLED` is initially `false`. Its preflight job has no OIDC permission and fails before the cloud job when disabled. The later cloud job uses environment `azure-lab-plan` or `azure-lab-apply`; both are restricted to main and require review by javedkumail. Administrator bypass is disabled. Self-review prevention is off because this is a single-owner personal lab; an independent reviewer remains a future option.

Use separate Entra client identities for plan and apply, configured as environment variables below. No client secret, Azure credential JSON or GitHub Project token is required. Before creating federation, verify the actual GitHub subject format/customization, issuer and `api://AzureADTokenExchange` audience for each environment. Do not assume a text subject pattern or reuse the old personal-owner subject: GitHub can use immutable repository/owner identifiers. There are no Azure federated credentials to verify yet.

The plan identity needs only the relevant Azure reads plus state-blob data access needed for locking. The apply identity needs the exact dedicated resource-group creation/update scope and the same dedicated state access. Do not default to subscription-wide Owner/Contributor; define the narrow custom role or bootstrap scope after the personal subscription is confirmed. Creating a resource group requires permission at its parent scope, which must be included in the reviewed bootstrap design.

## Required configuration before enabling execution

Set these on both protected environments, using different AZURE_CLIENT_ID values for plan/apply. IDs are configuration, not secret tokens; use supported GitHub configuration storage. Supply values only after G2/G3 decisions and authenticated personal ownership checks.

| Variable | Purpose |
| --- | --- |
| AZURE_CLIENT_ID | Environment-specific OIDC identity |
| AZURE_TENANT_ID / AZURE_SUBSCRIPTION_ID | Exact confirmed personal target |
| TF_STATE_RESOURCE_GROUP | Dedicated bootstrap group, with rg-ai-sre- prefix |
| TF_STATE_STORAGE_ACCOUNT / TF_STATE_CONTAINER | Pre-existing protected remote-state location |
| LAB_RESOURCE_GROUP | Separate new rg-ai-sre- foundation group |
| AZURE_LOCATION | Confirmed region, no default |
| LAB_EXPIRES_ON | Future review date, YYYY-MM-DD |
| AZURE_MONTHLY_BUDGET / AZURE_BUDGET_CURRENCY | Confirmed positive budget and currency; this check does not create an Azure budget alert |

The state key is fixed to `ai-sre-observability/foundation.tfstate`. Bootstrap must establish state storage/container ownership, Entra data-plane access, locking, encryption/recovery, disabled anonymous blob access and reachable networking. Account keys and SAS tokens are not used. Review bootstrap/state lifecycle separately; this root cannot create its own backend. Do not point it at customer or unrelated state.

After checking the actual identities, roles, state, target, concrete scope and cost authorization, set repository variable AZURE_DEPLOYMENT_ENABLED to true. The setup task leaves it false and sets no Azure IDs or placeholder credentials.

## Plan and apply

1. From main, manually run Terraform foundation delivery with operation plan. Pass the required environment review. The workflow checks target inputs, logs in through OIDC, matches the selected Azure context, initializes remote state and creates a private saved plan.
2. Review the source commit and foundation resource change. The public run summary includes only action counts and a deterministic plan SHA256. Raw JSON, variables, state and the binary plan remain on the ephemeral runner and are removed. Review source/inputs through the approved operator process; do not upload raw plan/state to a public PR or artifact.
3. On the same main commit, manually run operation apply with that reviewed SHA256. Approve the protected apply environment. It generates a new private plan, rejects deletions/replacements or scope beyond the single foundation group, and requires a matching fingerprint before applying that exact saved plan in the same job.
4. Source, state, variables or plan changes invalidate the fingerprint and require a new plan review. Only timestamp differences are excluded. Terraform plan/apply operations are serialized by one workflow concurrency group.

No automatic apply on push/PR, public raw-plan artifact, destroy workflow or broad Kubernetes deployment is configured. CI evidence proves preparation, while P3.3/P3.5 still require real bootstrap/federation/deployment evidence. Keep local backend, CI, Azure and Managed results distinct.
